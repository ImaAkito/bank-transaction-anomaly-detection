# Система выявления аномальных банковских транзакций

Программный комплекс для дипломного проекта: анализирует банковские операции **в контексте динамического профиля клиента**, рассчитывает степень аномальности (0–1), уровень риска, причины срабатывания и передаёт результат специалисту в веб-интерфейс почти в реальном времени.

> Оценка модели является аналитической. Система не трактует аномальную операцию как мошенническую: итоговое решение принимает специалист.

## Архитектура

```
Симулятор ──REST (X-API-Key)──▶ FastAPI ──▶ очередь Redis, партиции по клиенту ──▶ Воркеры 0..N ─┐
(или банк)   /api/transactions/enqueue                                    предобработка → признаки → профиль →
             /api/transactions (синхронно)                                модель → оценка/риск → интерпретация
                                                                                                 ▼
 React-интерфейс (вход, роли) ◀── WebSocket ◀── Redis pub/sub ◀── PostgreSQL (схема — миграции Alembic)
                                                                                                 ▲
             Сервис переобучения: по расписанию или при дрейфе (PSI) ──▶ общий том с моделью ──┘
                                  (API и воркеры перечитывают изменённый артефакт сами)
```

| Компонент из задания | Реализация |
|---|---|
| Приём транзакций | `app/api/transactions.py`: синхронный `POST /api/transactions`, асинхронный `POST /api/transactions/enqueue` (Redis), идемпотентность по `transaction_id` |
| Предобработка | `app/domain/preprocessing.py`: валидация, нормализация, пересчёт в базовую валюту |
| Формирование признаков | `app/domain/features.py`: 26 признаков в 5 группах (+5 опциональных популяционных) (сумма, время, частота, новизна, история) |
| Поведенческий профиль | `app/domain/profile.py`: инкрементальный профиль (Welford, окно сумм, гистограммы часов/дней, частоты категорий, каналов, валют, получателей) |
| Машинное обучение | `app/ml/train.py`, `app/ml/model.py`: Isolation Forest (базовый), LightGBM (при наличии разметки) |
| Степень аномальности | калибровка сырой оценки в [0, 1], пороги риска в артефакте модели |
| Интерпретация | `app/ml/explain.py`: причины на русском («сумма в 8,4 раза превышает медиану…») + SHAP-вклады признаков |
| Серверное API, БД | FastAPI, SQLAlchemy, PostgreSQL (SQLite для разработки); схема — миграции Alembic (`backend/migrations`) |
| Аутентификация и роли | `app/security.py`, `app/api/auth.py`: вход по паролю (PBKDF2), подписанные токены; роли viewer / analyst / admin, API-ключ для приёма транзакций |
| Часовой пояс клиента | поле `timezone` (IANA) в транзакции, запоминается у клиента; признаки времени суток и дня недели считаются по местному времени |
| Мониторинг модели | `app/ml/drift.py`: PSI признаков и сдвиг доли оповещений относительно обучения (`/api/model/drift`); сравниваются только операции клиентов с историей от 20 операций, признак длины истории исключён — иначе новые клиенты на старте давали ложный дрейф |
| Автоматическое переобучение | `app/ml/retrain.py`: по накопленной истории, по расписанию или при дрейфе, с проверкой кандидата и архивом прежних версий |
| Веб-интерфейс | `frontend/`: React + TypeScript; поток, фильтры, карточка операции, профиль клиента, решения специалиста |
| Журналирование и мониторинг | JSON-логи с `request_id`, `/api/health`, `/api/stats`, Prometheus `/metrics` (API и воркер) |
| Симулятор | `app/simulation/`: генератор клиентов-персон с размеченными аномалиями и потоковая отправка в API |
| Контейнеризация | `docker-compose.yml`: postgres, redis, trainer, api, worker-0, worker-1, retrainer, frontend, simulator |

## Быстрый старт (Docker)

```bash
docker compose up --build
```

Интерфейс: <http://localhost:8080> (вход: `admin` / `admin`, задаётся `ADMIN_USERNAME` / `ADMIN_PASSWORD`), API и Swagger: <http://localhost:8000/docs>. Сервис `trainer` обучает модель при первом запуске; API применяет миграции и создаёт администратора; два воркера делят партиции очереди; симулятор передаёт операции с ключом `INGEST_API_KEY`; `retrainer` проверяет необходимость переобучения каждые 30 минут. Настройки — в `.env.example`.

> Проверено в среде разработки: образы собраны из Dockerfile как есть, `docker compose up` поднял все 9 сервисов; вход, отказ без токена (401), миграция `0001` в PostgreSQL, распределение партиций между воркерами (`[0, 2]` и `[1, 3]`), дрейф, переобучение кнопкой с горячей перезагрузкой модели в API и воркерах. Библиотека `libgomp` для LightGBM копируется из промежуточного образа `python:3.11` (многоэтапная сборка), поэтому `apt-get` при сборке не нужен.

| Роль | Права |
|---|---|
| viewer | просмотр транзакций, клиентов, модели и дрейфа |
| analyst | то же и решения по операциям (автор решения — вошедший пользователь) |

Локально без Docker аутентификация выключена (`AUTH_ENABLED=false`), все запросы выполняются от имени администратора.

## Локальный запуск без Docker

```bash
make install                # зависимости backend и frontend
make train                  # обучение модели → backend/models/model.joblib
make api                    # API на :8000 (SQLite, очередь в памяти)
make simulator              # поток транзакций (в другом терминале)
make frontend               # интерфейс на :5173
make test                   # тесты backend
make experiments            # экспериментальная часть
```

Для очереди Redis и PostgreSQL задайте переменные (см. `.env.example`): `QUEUE_BACKEND=redis`, `REDIS_URL`, `DATABASE_URL`, запустите воркер `python -m app.worker`. Несколько воркеров: `QUEUE_PARTITIONS=4 WORKER_COUNT=2` и у каждого свой `WORKER_INDEX` (0, 1); операции одного клиента всегда попадают в одну партицию и обрабатываются по порядку.

Миграции применяются при старте API автоматически; вручную — `cd backend && alembic upgrade head`, новая миграция после изменения моделей — `alembic revision --autogenerate -m "описание"`.

Переобучение вручную — `python -m app.ml.retrain`, периодически — `python -m app.ml.retrain --loop` (параметры `RETRAIN_INTERVAL_HOURS`, `DRIFT_PSI_ALERT`, `RETRAIN_MIN_TRANSACTIONS`).

## Как работает оценка

1. Транзакция нормализуется; берётся профиль клиента **до** этой операции.
2. Признаки сравнивают операцию с профилем: отношение суммы к медиане клиента, z-оценка логарифма суммы, частота часа и дня недели, новизна категории/канала/получателя/валюты, число операций за час и сутки и др. Одна и та же функция используется при обучении и в эксплуатации.
3. Isolation Forest даёт сырую оценку; сигмоидная калибровка переводит её в [0, 1] (0,5 — квантиль 98% обучающих оценок, 0,9 — квантиль 99,5%). Пороги риска: средний ≥ 0,6, высокий ≥ 0,85 (переопределяются `RISK_MEDIUM`, `RISK_HIGH`).
4. Для операций со средним и высоким риском строятся текстовые причины, «характер отклонения» (сумма, время, категория, канал, получатель, валюта, частота) и SHAP-вклады.
5. Результат сохраняется, публикуется в WebSocket. Статус: `normal` или `needs_review`; специалист меняет его на `reviewed_normal` / `reviewed_suspicious`, каждое изменение пишется в историю срабатываний.

### Проектные решения

* **Холодный старт.** У короткой истории новизна категории — обычное явление. Признаки частот сглаживаются (псевдонаблюдения), бинарные признаки новизны и z-оценка ослабляются множителем `n / (n + 15)`, причины на коротких историях получают меньшую тяжесть. Без этого при прогоне симулятора большинство срабатываний приходилось на клиентов с историей менее 20 операций.
* **Что попадает в профиль.** Выбросы по сумме (≥ 5 медиан) и всплески частоты (≥ 3 операций за час) удерживаются вне «типичного поведения» до решения специалиста («нормальная» — операция добавляется в профиль). Новизна категории, канала или времени в профиль попадает, чтобы система училась легитимным изменениям привычек. Правило зависит только от признаков и одинаково применяется при обучении и в эксплуатации. Ранее использовавшийся вариант «удерживать истинные аномалии по меткам» давал завышенные офлайн-метрики, недостижимые в эксплуатации, поэтому от него отказались (доступен как `hold_policy="labels"` для сравнения).
* **Метки симулятора** сохраняются отдельно (`simulation_label`), в модель не передаются и используются только для проверки на дашборде.

## Экспериментальная часть

`make experiments` → `backend/experiments/results/` (`report.md`, `summary.json`, графики). Протокол: 3 независимых набора (по ~56 тыс. транзакций, ~1,3% аномалий), хронологическое разбиение 65/15/20, профили накапливаются последовательно; подбор параметров по PR-AUC на валидации; метрики на тесте, среднее ± σ.

Выдержка (Precision/Recall/F1 — порог по максимуму F1 на валидации; последний столбец — фиксированный бюджет оповещений, без подбора порога):

| LOF | без учителя | 0,43 | 0,51 | 0,47 | 0,939 | 0,472 | 0,59 / 0,43 |
| One-Class SVM | без учителя | 0,72 | 0,43 | 0,53 | 0,961 | 0,555 | 0,65 / 0,47 |
| Elliptic Envelope | без учителя | 0,40 | 0,49 | 0,33 | 0,958 | 0,403 | 0,37 / 0,27 |

| Правило: минимальная частота | без учителя | 0,16 | 0,34 | 0,22 | 0,797 | 0,139 | 0,21 / 0,15 |
| Логистическая регрессия | с учителем | 0,79 | 0,71 | 0,74 | 0,989 | 0,810 | 0,88 / 0,63 |

Что видно из результатов (на синтетических данных):
* среди методов без учителя Isolation Forest имеет наибольший PR-AUC; при наличии разметки контролируемые модели (XGBoost, LightGBM, логистическая регрессия) выше;
* признаки профиля клиента существенно влияют на качество: набор «только сумма и время» без профиля даёт PR-AUC 0,10 против 0,66 у полного набора; наибольший вклад у групп «сумма» и «новизна»;
* по типам аномалий (порог без меток) Isolation Forest почти всегда находит новую категорию и иностранный канал/валюту (recall ≈ 1,0), резкое превышение суммы находит в 69% случаев, ночные операции в 83%, всплески частоты (51%) и умеренные комбинированные отклонения (52%) остаются слабым местом.

**Улучшение признаков.** Добавлены признаки суммы относительно привычной для категории (`cat_amount_zscore`, `cat_log_dev`), удалённости от привычного часа по круговому среднему (`hour_dev`) и интервала с предыдущей операции относительно обычного (`gap_ratio`). Изменение PR-AUC на тех же трёх наборах: Isolation Forest 0,556 → 0,664, One-Class SVM 0,475 → 0,555, XGBoost 0,752 → 0,821, LightGBM 0,431 → 0,829. Генератор задаёт суммы по категориям, поэтому выигрыш на реальных данных может оказаться меньше [Inference].

Ограничения: данные синтетические, поэтому абсолютные значения метрик не переносятся на реальные банковские данные [Inference]. CatBoost не включён.

### Эксперименты на IBM Credit Card Transactions

Загрузчик `app/ml/ibm_loader.py` приводит набор IBM (TabFormer) к формату проекта: пользователь → клиент, MCC → категория, тип использования карты → канал, штат мерчанта → категория получателя, `Is Fraud?` → метка. Возвраты (сумма ≤ 0) отбрасываются, берётся детерминированная доля пользователей и период с заданного года.

```bash
cd backend
python -m app.ml.experiments --dataset ibm --ibm-path /путь/к/card_transaction.v1.csv \
    --ibm-user-fraction 0.05 --ibm-from-year 2010 --out experiments/results_ibm
```

Полный цикл на своём компьютере:

```bash
git clone https://github.com/ImaAkito/bank-transaction-anomaly-detection.git && cd bank-transaction-anomaly-detection
git checkout claude/bank-anomaly-detection-ml-lc1px8
pip install -r backend/requirements-dev.txt
# 1) скачать набор с Kaggle (нужен аккаунт) и положить вне git-отслеживаемых файлов, например backend/datasets/
mkdir -p backend/datasets && kaggle datasets download -d ealtman2019/credit-card-transactions -p backend/datasets --unzip
cd backend
# 2) эксперименты (результаты попадут в experiments/results_ibm)
python -m app.ml.experiments --dataset ibm --ibm-path datasets/<имя_файла>.csv --out experiments/results_ibm
# 3) при желании обучить рабочую модель на IBM
python -m app.ml.train --dataset ibm --ibm-path datasets/<имя_файла>.csv --out models/model.joblib
# 4) залить в git только результаты
git add experiments/results_ibm && git commit -m "Результаты на IBM" && git push
```

Каталоги `datasets/`, файлы `*.csv`, `*.zip`, `*.parquet` и `backend/models/` исключены через `.gitignore`, поэтому набор и артефакт модели в git не попадут; `git status` перед коммитом стоит проверить. Для набора в десятки миллионов строк нужны несколько гигабайт памяти и время: уменьшайте `--ibm-user-fraction` (по умолчанию 0,05).

**Полный объём (~24 млн операций)** — потоковая обработка `app/ml/large.py`: файл раскладывается по партициям клиентов, признаки считаются параллельно (float32), в обучении сохраняются все мошеннические и доля `--negative-rate` обычных операций, тестовый период — полностью:

```bash
python -m app.ml.experiments --dataset ibm --ibm-path datasets/credit_card_transactions-ibm_v2.csv --ibm-full \
    --workers 8 --negative-rate 0.2 --feature-groups amount,novelty,population --out experiments/results_ibm_full
```

Дополнительно: `--population-mode causal` считает популяционные частоты по операциям строго до текущей (без заглядывания в будущее); в сравнение методов добавлен CatBoost. Число партиций по умолчанию подбирается по размеру файла (`--parts`, ~150 тыс. строк на партицию).

Замер на макете в формате IBM (1,99 млн строк, 144 МБ, 16 партиций, 4 процесса, `--negative-rate 0.2`): 91 с, пиковая память главного процесса 939 МБ, процесса-обработчика 236 МБ, итоговая таблица признаков 104 МБ (734 тыс. строк). [Inference] Для полного файла (~24 млн строк, в 12 раз больше) ожидается порядка 18–20 минут на 4 процессах и около 1,3 ГБ на таблицу признаков; на компьютере с 8–16 ГБ памяти разумно `--workers 4–8`, при нехватке памяти — уменьшить `--negative-rate` или увеличить `--parts`.

Статус: загрузчик и выборка 5% пользователей проверены на реальном файле (результаты ниже); полный объём и режим `causal` проверены только на макете, так как хосты с данными недоступны из среды разработки.

### Протокол финальной проверки (отложенный период)

Группы признаков выбирались по результатам на тестовом периоде данных 2010+ (три прогона полного объёма), поэтому этот тест стал частью разработки. Окончательная оценка выполняется на периоде, который не использовался ни для обучения, ни для выбора решений:

| Этап | Данные | Что на нём решается |
|---|---|---|
| Обучение / валидация / тест разработки | 2010 – конец файла, разбиение 65/15/20 | выбор методов, групп признаков, параметров |
| Финальная проверка | отдельный период до 2010 года, тот же протокол 65/15/20 внутри периода | только итоговая оценка; конфигурация не меняется |

Конфигурация, замороженная до финального прогона:

* группы признаков: `amount,velocity,novelty,history,population` (без `time`), режим популяционных частот `fixed`;
* основная модель — One-Class SVM, базовая и альтернативная — Isolation Forest, модели с учителем — сравнительные методы;
* основные критерии — полнота при бюджете проверки 1% операций и AP (Average Precision); ROC-AUC — дополнительный;
* сетки параметров и пороги — те же, что при разработке (подбор только по валидации внутри периода).

```bash
python -m app.ml.experiments --dataset ibm --ibm-path datasets/credit_card_transactions-ibm_v2.csv --ibm-full \
    --ibm-from-year 2003 --ibm-to-year 2009 --final --workers 4 \
    --feature-groups amount,velocity,novelty,history,population --out experiments/results_ibm_final
```

В режиме `--final` анализ групп признаков не выполняется, в отчёт записываются период и замороженная конфигурация. Ограничение: отложенный период расположен раньше периода разработки, а не позже — более поздних данных в наборе нет; проверка показывает перенос конфигурации на независимый временной интервал, но не на будущее относительно разработки.

Метрика «PR-AUC» в отчётах — это Average Precision (`sklearn.metrics.average_precision_score`), а не трапециевидная площадь под PR-кривой; в отчётах она подписана как «AP (PR-AUC)».

### Результаты на IBM Credit Card Transactions (5% пользователей, с 2010 года)

Запуск выполнен на реальном файле: ~0,72–0,92 млн операций на набор, доля мошенничества 0,09–0,16%, на тесте 168–237 мошеннических операций, 3 выборки пользователей. Метрики на тесте (порог по F1 на валидации):

| Метод | Precision | Recall | ROC-AUC | PR-AUC |
|---|---|---|---|---|
| Isolation Forest | 0,009 | 0,27 | 0,858 | 0,007 |
| One-Class SVM | 0,020 | 0,13 | 0,779 | 0,007 |
| Логистическая регрессия | 0,035 | 0,07 | 0,926 | 0,023 |
| XGBoost (до регуляризации) | 0,019 | 0,003 | 0,892 | 0,008 |
| LightGBM (до регуляризации) | 0,006 | 0,03 | 0,413 | 0,004 |

Вывод: на реальных размеченных данных система работает **существенно хуже**, чем на синтетике. Базовая доля мошенничества ≈ 0,1%, поэтому PR-AUC 0,007 у Isolation Forest означает лифт в 5–7 раз над случайным выбором, а при 1,8% помеченных операций точность около 1%. Ранжирование при этом осмысленное (ROC-AUC 0,86).

Наблюдения (интерпретация [Inference], проверяется диагностикой ниже):
* нестабильность LightGBM (ROC-AUC 0,41, остановка на 2-й итерации) указывает на дрейф: связь признаков с меткой в обучающем периоде отличается от тестового;
* в абляции удаление группы «time» повышает PR-AUC (0,007 → 0,011), а набор «сумма + новизна» без остальных даёт лучший PR-AUC (0,013): часть признаков разбавляет сигнал; без группы «novelty» ROC-AUC падает с 0,86 до 0,67;
* метка в IBM означает мошенничество, а не отклонение от профиля клиента, поэтому часть мошеннических операций по признакам не отличима от обычных.

**Диагностика набора** (`python -m app.ml.diagnostics`, 915 тыс. операций, 868 мошеннических, 100 клиентов):
* сильнейший сигнал — регион получателя: у «italy» 63,5% мошенничества (183 из 288 операций), у «haiti» 100%; одномерный ROC-AUC `recipient_cat_freq` на тесте 0,012, то есть 0,988 в обратной ориентации;
* онлайн-канал: 0,42% мошенничества против 0,02% у swipe; редкие по всему набору категории (электроника 6,5%, MCC 5094 5,3%);
* нестационарность: доля мошенничества по годам от 0% (2011) до 0,21% (2010); в валидации 0,043%, в обучении 0,108%, поэтому порог «по F1 на валидации» для бустингов нестабилен (XGBoost получил нулевую полноту);
* 10% клиентов дают 39,7% мошенничества; медианная сумма мошеннических операций 70,8 против 31,3;
* нестабильные признаки (знак одномерного AUC меняется между обучением и тестом): `hour_sin`, `is_night`, `weekday_freq`.

**Второй прогон** (`--feature-groups amount,novelty`, 14 признаков): Isolation Forest ROC-AUC 0,894, PR-AUC 0,023 (было 0,858 / 0,007), One-Class SVM 0,858 / 0,021, логистическая регрессия 0,931 / 0,023. Метрики бустингов по порогу с валидации ненадёжны (нулевая полнота у XGBoost).

**Третий прогон** (`--feature-groups amount,novelty,population`, 20 признаков, те же 3 выборки):

| Метод | ROC-AUC | PR-AUC | Топ 0,1%: P / R | Топ 1%: P / R |
|---|---|---|---|---|
| Isolation Forest | 0,966 | 0,061 | 0,13 / 0,11 | 0,045 / 0,40 |
| One-Class SVM | 0,969 | 0,062 | 0,11 / 0,10 | 0,059 / 0,54 |
| Правило: минимальная частота | 0,957 | 0,015 | 0,02 / 0,01 | 0,015 / 0,14 |
| Логистическая регрессия | 0,843 | 0,010 | 0,03 / 0,02 | 0,009 / 0,08 |
| XGBoost | 0,849 | 0,005 | 0,01 / 0,00 | 0,003 / 0,02 |
| LightGBM | 0,768 | 0,007 | 0,01 / 0,00 | 0,009 / 0,08 |

PR-AUC Isolation Forest вырос в 9 раз относительно первого прогона (0,007 → 0,061). При доле мошенничества ≈ 0,1% точность 13% в топ-0,1% означает лифт около 130 раз над случайным выбором. Без группы `population` PR-AUC падает до 0,021, а набор «только population + сумма/время» (7 признаков) даёт ROC-AUC 0,986 и PR-AUC 0,062. Модели с учителем остаются слабыми (XGBoost остановился на 2-й итерации).

**Четвёртый прогон** (хронологический подбор и гибрид, те же признаки): LightGBM с окнами по времени — PR-AUC 0,004, гибрид — 0,006, при этом средний PR-AUC на окнах внутри обучающего периода у обоих 0,15–0,16. Бустинг хорошо работает внутри периода обучения и не переносится на следующий период: вероятно, деревья запоминают конкретные значения редкости (регион, категорию), а мошенничество в тестовом периоде приходит через другие значения [Inference]. Методы без учителя (Isolation Forest, One-Class SVM) такой зависимости не выучивают и остаются лучшими на IBM. Для проверки добавлен режим монотонных ограничений (`--monotone`, строки «LightGBM монотонный» и «Гибрид монотонный»): редкость и новизна могут только повышать оценку, частота — только понижать. На синтетике он не ухудшает качество (PR-AUC 0,84 против 0,85).

**Пятый прогон** (монотонные ограничения):

| Метод | ROC-AUC | PR-AUC | Топ 1%: P / R | PR-AUC на окнах обучения |
|---|---|---|---|---|
| LightGBM (окна по времени) | 0,707 | 0,004 | 0,003 / 0,02 | 0,152 |
| LightGBM монотонный | 0,858 | 0,014 | 0,023 / 0,21 | 0,087 |
| Гибрид монотонный | 0,882 | 0,014 | 0,022 / 0,21 | 0,079 |
| Isolation Forest | 0,966 | 0,061 | 0,045 / 0,40 | — |
| One-Class SVM | 0,969 | 0,062 | 0,059 / 0,54 | — |

Монотонные ограничения подтвердили гипотезу о запоминании: качество внутри периода обучения снизилось (0,15 → 0,08), а на тестовом периоде выросло в 3 раза (PR-AUC 0,004 → 0,014, полнота в топ-1% 0,02 → 0,21). Разрыв между обучением и тестом сократился, но методы без учителя остаются в 4 раза лучше по PR-AUC и в 2 раза по полноте в топ-1%.

**Итог по IBM:** на данных, где схемы мошенничества меняются во времени, обнаружение аномалий без учителя по поведенческому профилю и популяционной редкости переносится на новый период лучше, чем обучение с учителем на исторических метках; ограничение модели априорными знаниями («реже — подозрительнее») сокращает, но не устраняет разрыв.

**Рекомендация для IBM:** рабочая модель — Isolation Forest с группой `population` (`--feature-groups amount,novelty,population`).

**Что сделано по результатам.**
* Группа признаков `population` (опциональная, включается через `--feature-groups`): редкость категории, региона и канала среди **всех** клиентов (счётчики по обучающему периоду, без меток, хранятся в артефакте модели) и произведения «новый для клиента × редкий среди всех». На макете, где часть мошенничества уходит в редкие страны, PR-AUC Isolation Forest вырос с 0,437 до 0,595 (проверка механизма, не оценка на IBM). На синтетике без такой связи группа снижает PR-AUC Isolation Forest (0,68 → 0,54), поэтому по умолчанию она выключена.
* Таблица «фиксированный бюджет оповещений» (топ 0,1% / 0,5% / 1% операций по оценке): не зависит от порога, подобранного на малой валидации.
* Правило-эталон «минимальная частота» (категория, канал, регион, час); регуляризация бустингов.

### Контролируемые модели и гибрид

Для размеченных данных (`python -m app.ml.train --kind lightgbm|hybrid`):
* **LightGBM с хронологическим подбором:** глубина и число деревьев выбираются по среднему PR-AUC на нескольких скользящих окнах (обучение на прошлом, проверка на следующем окне) вместо одной маленькой валидации; вес положительного класса берётся как корень из отношения классов;
* **Гибрид (`hybrid`):** Isolation Forest обучается без меток, а его оценка подаётся в LightGBM как дополнительный признак (`iforest_score`); SHAP-вклады считаются по бустингу и включают этот признак;
* **пороги риска по бюджету оповещений** (средний ≥ 99-го, высокий ≥ 99,8-го процентиля оценок на валидации), а не по максимуму F1 на малой выборке.

На синтетике гибрид и LightGBM с окнами сопоставимы с лучшим бустингом (PR-AUC 0,86 и 0,85); там дрейфа нет, поэтому преимущество хронологического подбора ожидается на данных с дрейфом вроде IBM и требует проверки [Unverified].

Запуск для IBM (в отчёте появятся строки «LightGBM (окна по времени)» и «Гибрид»):

```bash
python -m app.ml.experiments --dataset ibm --ibm-path файл.csv --feature-groups amount,novelty,population --out experiments/results_ibm4
python -m app.ml.train --kind hybrid --dataset ibm --ibm-path файл.csv --feature-groups amount,novelty,population --out models/model.joblib
```

Запуск для IBM (Isolation Forest):

```bash
python -m app.ml.experiments --dataset ibm --ibm-path файл.csv --feature-groups amount,novelty,population --out experiments/results_ibm
python -m app.ml.train --dataset ibm --ibm-path файл.csv --feature-groups amount,novelty,population --out models/model.joblib
```

## Ограничения и дальнейшая работа

* модели с учителем на IBM остаются слабее методов без учителя из-за смены схем мошенничества во времени (см. результаты); монотонные ограничения сокращают разрыв, но не устраняют его;
* полный объём IBM и режим `--population-mode causal` проверены на макете, на реальном файле не запускались;
* автоматическое переобучение поддерживает Isolation Forest (метки не нужны); модели с учителем переобучаются вручную через `app.ml.train`;
* в эксплуатации популяционные частоты фиксируются при обучении и обновляются переобучением;
* профиль хранит не более 200 последних моментов времени и 100 последних сумм.
